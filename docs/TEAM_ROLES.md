# 3인 분업: 인지 / 판단 / 제어

각 파트는 **다른 두 파트를 고정하고 자기 파트만 바꿔서** 평가한다. 처음에는 고정 대상을 GT 오라클이나 기준 구현으로 두고, 각 파트가 개발되면 최신 버전으로 바꿔 끼운다(통합 빌드).

> GT 오라클(시뮬레이터 정답)은 **개발 전용**이다. 런타임에 정답을 쓰면 과제 규칙 위반이므로(R-07) 제출 패키지에는 절대 넣지 않는다. 오라클 코드는 패키지 밖 `experiments/oracle/`에만 둔다.

---

## 1. 파이프라인과 경계(인터페이스)

```
카메라 · IMU · odom
      │
  [ 인지 ]  차선 감지 → 차선 기록(지도) → 자세 보정
      │      ▶ 차선 경로 (Route)
  [ 판단 ]  길 선택 · 종점 · 복구 · 속도 계획
      │      ▶ 목표 궤적 (Trajectory)
  [ 제어 ]  경로 추종 · 명령 제한
      │      ▶ /cmd_vel
   로봇 (Gazebo / 실물)
```

**차선 경로 (인지 → 판단)**: 로봇 앞쪽 경로 하나다.

| 항목 | 내용 |
|---|---|
| 점 목록 | odom 좌표 (x, y, 높이 z), 약 2 cm 간격, 가까운 점부터 |
| 허용 폭 | 점마다 좌우 허용 폭. 기본 ±0.10 m이고, 바퀴가 선을 밟지 않는 범위는 ±0.12 m다 |
| 속성 | 교차로(직진 통과), 끊긴 구간, 언덕(경사), 장애물 우회 구간, 종점 T자 |
| 끝 상태 | `open`(아직 안 보임), `t`(종점), `len`(길이 제한) |
| 신뢰도 | 점마다 또는 구간마다 0–1 |

**목표 궤적 (판단 → 제어)**

| 항목 | 내용 |
|---|---|
| 점 목록 | 실제로 달릴 경로. 허용 폭 안에서 최적화된 것이고, 로봇 좌표다 |
| 목표 속도 | 점마다 목표 선속도 |
| 행동 표시 | 일반 추종, 제자리 회전, 정지(종점), 복구 탐색 |

**지금 코드에서의 위치** (분리 작업 전)
- 인지: `perception/`(rule, dl), `vision.py`(BEV 투영), `line_map.py`(지도), `follower_node.py`(자세 추정)
- 판단: `line_map.trace`(길 선택), `follower_node.py`(종점, 복구), `control/rule.py` 앞부분(속도 계획)
- 제어: `control/rule.py` 뒷부분(pure pursuit, 명령 제한)
- 리드가 판단을 `planning/` 플러그인으로 분리하고, 위 두 인터페이스를 코드로 고정한다(6장).

## 2. 인지 (차선 감지 · 차선 기록 · 학습)

| | 내용 |
|---|---|
| **개선하는 것** | 차선 감지(분할 모델 / 임계값), 차선 기록(지도 누적, 끊김 보완), 자세 보정(코너마다 지도가 밀리는 문제), 언덕의 3D 위치(깊이), 장애물 검출, 모델 학습 |
| **고정하는 것** | 판단은 기준 판단(지금 사용자 패키지)으로, 제어는 기준 제어로 둔다 |
| **혼자 보는 지표 (오프라인, 주행 불필요)** | 카메라로 만든 경로와 GT 경로의 차이. 평지, 언덕, 코너 직후, 교차로 구간별로 잰다. 라인 IoU와 처리 시간(CPU 33 ms 안)도 본다 |
| **주행 지표** | 기준 판단·제어로 `hills60`, `official_like50`을 돌려 완주율을 본다. 같은 맵의 **GT 오라클 결과와의 격차**가 인지의 남은 몫이다 |
| **도구** | `experiments/eval/perception_offline.py`, `hill_geometry_offline.py`, `experiments/user_base/compare_map.py`, `run_user_dump.py` |

**현재 수치 (2026-11-24)**
- **병목:** 같은 제어에서 카메라 경로는 0/10 완주, GT 경로는 6/10 완주였다(hills60 앞 12맵).
- **지도 오차:** 직선은 1–3 cm다. 급코너를 돌 때마다 지도가 13–25 cm 밀린다. 언덕에서 평면 가정 IPM은 21.8 cm 틀리고, 선 폭 기반으로는 1.2 cm다.
- **감지:** U-Net v3는 라인 IoU 0.963, CPU 18 ms다. 임계값 방식은 어두운 상자를 선으로 잘못 잡는다.

**목표:** 카메라 경로만으로 GT 오라클과의 완주율 격차를 없앤다.

## 3. 판단 (차선이 있을 때 어떻게, 얼마나 빠르게)

| | 내용 |
|---|---|
| **개선하는 것** | 교차로, 코너 원, 연결 교차로, 끊긴 길에서의 길 선택. 종점 판정(`confirm_finish` 훅). 길을 놓쳤을 때 복구. 속도 계획(코너 진입, 언덕, 내리막). 허용 폭 안에서 가장 빠른 경로(레이싱 라인). 장애물 우회 경로 |
| **고정하는 것** | 인지는 **GT 오라클 경로**로 둔다(레벨 0 → 1 → 2로 올린다). 제어는 기준 제어로 둔다 |
| **지표** | 오라클 **레벨 2**에서 `hills60`, `official_like50`, `obstacles100` 완주율과 랩타임 |
| **도구** | `experiments/oracle/run_oracle.py`(`ORACLE_LEVEL`), `bench.py`, `summarize_suite.py`, `failure_locus.py` |

**오라클 레벨**
| 레벨 | 내용 | 용도 |
|---|---|---|
| 0 | 완벽한 GT 경로 | 판단 로직 자체를 검증한다 |
| 1 | 앞 0.85 m까지만 보이고, 0.31 m는 사각지대 | 시야 제한에 대응한다 |
| 2 | 레벨 1 + 잡음(약 1.5 cm), 지연(약 0.1 s), 코너마다 13–25 cm 밀림 | **합격 판정에 쓴다.** 실제 인지와 비슷한 조건이다 |

**현재 수치:** 오라클 레벨 0에서 6/10, **레벨 2에서 2/11** 완주(평균 59.5%). 남은 실패는 normal_9001_m 10.57 m, hard_9002_m 9.44 m, easy_9009 10.60 m, hard_9008 12.77 m 이탈과 normal_9007_m 15.82 m 정체다.

## 4. 제어 (실제 차 제어 · PID 최적화)

| | 내용 |
|---|---|
| **개선하는 것** | 경로 추종(pure pursuit, Stanley, 횡오차·방향 오차 PID, MPC). 명령 제한(가속도, 각가속도). 미끄러짐 억제. 내리막 과속 억제. 실물에서는 모터 PID와 오도메트리 보정 |
| **고정하는 것** | 인지는 GT 오라클로, 판단은 **기준 판단이 만든 목표 궤적**으로 둔다(같은 궤적을 반복 재생하면 비교가 공정하다) |
| **지표** | 추종 오차(횡오차 p95, 바퀴 선 접촉), 진동(각속도 변화량), 미끄러짐 이벤트, 완주율과 랩타임 |
| **도구** | `bench.py` + `telemetry.py`(속도, 가속도, 각속도, 횡오차를 s축으로 기록), 2D 시뮬레이터(`experiments/eval/corner_tune_2d.py`, `controllers_2d.py`) |

**참고**
- Gazebo의 차동구동은 `/cmd_vel`을 거의 이상적으로 따라간다. 그래서 시뮬레이션에서는 **경로 추종과 명령 제한**이 핵심이고, 모터 PID는 실물(Orin)에서 중요해진다.
- **출발점 (2D, 30맵):**
  - 제자리 회전을 60°에서 40°로 일찍 시작하고 최대 각속도를 3에서 1.5 rad/s로 낮추니 10/30이 18/30이 됐다. 랩타임은 같다.
  - Nav2 Regulated Pure Pursuit 규칙은 13/30이다.

## 5. 고정과 교체 일정

| 단계 | 인지 | 판단 | 제어 |
|---|---|---|---|
| **1. 시작** | 기준 판단·제어로 고정하고 오프라인 지표로 개발 | GT 오라클 레벨 0 + 기준 제어 | GT 오라클 + 기준 판단 궤적 |
| **2. 단련** | 같음 | 오라클 레벨 1 → 2 | 오라클 레벨 2 |
| **3. 통합 빌드 (2–3일마다)** | 최신 판단·제어를 받아 주행 확인 | 최신 인지를 받아 오라클과의 격차 확인 | 최신 인지·판단을 받아 확인 |
| **4. 최종** | 오라클을 빼고 실제 인지 → 판단 → 제어로 제출 | | |

**통합 빌드 규칙**
- 회귀 세트: 공식 트랙 10회, `hills60`, `official_like50`(+ `obstacles100`). **GPU 없는 Docker** 실행도 확인한다(채점 PC 사양 미상).
- 채택 조건: 공식 트랙 10회 중 9회 이상. 세트 완주율이 이전 통합 빌드보다 낮아지지 않아야 한다.
- 결과 기록: `summarize_suite.py` 표, `failure_locus.py` 요소별 실패, 텔레메트리 그림.
- 브랜치: `perception/<이름>`, `planning/<이름>`, `control/<이름>`. 통합은 기준 브랜치(`wlsgur0317/two-track`)에서 한다.

## 6. 공용 작업 (리드 담당)

1. 판단을 `planning/` 플러그인으로 분리하고, 차선 경로와 목표 궤적 인터페이스를 코드로 고정한다. 기존 `rule` 모드의 공식 트랙 63–64초가 유지되는지 확인한다.
2. 오라클을 **두 지점**에 끼울 수 있게 한다.
   - 차선 경로 자리(판단 개발용) — 지금 있다.
   - 목표 궤적 자리(제어 개발용) — 새로 만든다.
3. 채점, 테스트 세트, 텔레메트리, 제출 Docker를 관리한다.
4. 통합 빌드를 돌리고 결과를 공유한다.
