# line_follower(rule 모드) 안전성 실측 요약

- 대상: `src/line_follower` `follower_node.py`, `config/rule.yaml`(sion 브랜치, 코드 수정 없음). 실행은 `experiments/user_base/run_user.py`로 했고, 8번 항목만 `ros2 launch line_follower line_follower.launch.py gui:=false`를 그대로 실행했다.
- 환경: `rp/ros2:jazzy-lab` 컨테이너 `lf_s`, headless Gazebo Harmonic. 실행마다 ROS 도메인 84–89 중 비어 있는 것 하나(G2 bench는 70–79)와 고유 `GZ_PARTITION`(`lf_s_*`)을 썼고, 동시에 실행한 시뮬레이션은 최대 2개다.
- 측정: Gazebo 실제 자세 `/world/line_track/dynamic_pose/info`(평가 전용, 로봇 제어에는 사용하지 않음), `/cmd_vel` 구독, 상자 접촉 센서. "5 s 이동"은 고장 시점 자세에서 5 s(시뮬레이션 시간) 뒤 자세까지의 직선 거리다.
- 규모: 28개 시나리오 62회 + G2 bench 12회, 실패한 실행 없음. 모든 시나리오를 2회 이상 실행했다. 회차별 결과는 `runs/<시나리오>/<시각>_r<k>/result.json`(궤적 `trace.npz`, 로그 `*.log`), 전체 모음은 `all_results.json`이다.
- 재현: 컨테이너 `/ws`에서 `python3 experiments/eval/safety_faults.py run all --repeat 2 --jobs 2`, 이름으로 하나씩 고를 때는 `... run sigkill camera_loss`, 목록은 `... list`, 집계는 `... summarize`, G2 bench는 `... run obstacles`.

## 판정 기준

- **A (무시 가능)**: 시뮬레이션 대회 평가에서 일어날 수 없거나, 일어나더라도 이미 그 회차가 끝난 뒤라 결과가 달라지지 않는다. 또한 계획된 실물(Jetson Orin) 주행에서도 위험이 없거나, 원래 패키지 밖(하드웨어 watchdog·E-STOP, `docs/design.md` §9.2)이 맡아야 하는 일이다.
- **B (실제 문제)**: 평가 맵에서 주행 중단, 충돌, 잘못된 완주 판정(엉뚱한 곳에서 정지하거나 결승점에서 정지하지 않음)을 일으킨다. 또는 실물로 옮겼을 때 로봇이 멈추지 않고 계속 움직이는 위험이 된다. "B(실물)"은 대회 점수에는 영향이 없지만 실물 위험 때문에 B로 판정한 것이다.
- 시뮬레이션 대회라는 점만으로 A가 되지는 않는다. 평가 맵(제공 트랙과 다르고 더 어렵고 상자가 있을 수 있음)에서 재현되거나 실물에서 사람이나 물체를 칠 수 있으면 B다.

## B 항목별 권고

1. **1a·1b 종료 시 0 미발행**: `rclpy.init(signal_handler_options=SignalHandlerOptions.NO)`로 초기화하고 SIGINT/SIGTERM을 직접 처리한다. 실행기를 멈춘 뒤 컨텍스트가 살아 있을 때 0 Twist를 여러 번 발행하고(`wait_for_all_acked` 등), 그다음에 `shutdown`한다. 구 `safety_guard_node.cpp`의 `stop_before_shutdown()`과 같은 방식이다. 수정한 뒤 `safety_faults.py run sigint sigterm`으로 확인한다.
2. **1c 크래시 시 마지막 명령 유지**: 노드 안에서는 고칠 수 없다. `/cmd_vel` 앞에 작은 watchdog 릴레이를 둔다(입력이 0.3 s 끊기면 0을 발행하는 별도 프로세스, 또는 `twist_mux` 타임아웃). 실물에서는 펌웨어나 드라이버 쪽 명령 타임아웃과 물리 E-STOP이 필수다(design §9.2, §12 F).
3. **2·3a·3b 센서 고장 시 계속 주행**: `control()` 앞에 신선도 게이트를 넣는다. 마지막 영상·odom·IMU 수신 나이가 0.5 s를 넘으면(벽시계와 스탬프 둘 다 확인) 0을 발행하고 래치한다. 기억 경로 주행에는 속도 상한(예 0.06 m/s)과 거리 상한을 둔다. IMU가 끊기면 odom 헤딩으로 되돌아가거나 정지한다. 제자리 회전에는 시간 예산(예 8 s)을 둔다.
4. **5a·5b 완주 게이트**: 고정 `finish_min_dist`(14 m)만 믿지 않는다. 출발 T를 벗어난 뒤(예 1 m 이상 주행) T 후보를 받아들이되, T 바 너머가 실제로 관측됐는데 선이 없는지 확인하고 나서 `t_point`를 고정한다(시야 끝의 미관측과 구별). 고정한 뒤에도 바 너머로 선이 보이면 해제한다. 출발 T는 출발 자세 근처에서 기억해 두고 제외한다. 맵 길이를 가정하는 상수는 평가 맵에서 깨진다.
5. **6 장애물**: 최소한 "부딪히기 전에 멈춤"부터 넣는다. 카메라에서 지면 평면에 맞지 않는 어두운 영역(폭이 2 cm 선보다 훨씬 넓고, 위로 서 있어 BEV에서 사다리꼴로 늘어나는 덩어리)을 장애물로 분류하고, 그 픽셀은 선 마스크에서 뺀다. 그다음 좌우 우회와 선 복귀를 붙인다. 상자가 있는 G2 맵과 상자를 뺀 대조 맵(`obs_*`, `nobox_*`)을 같이 돌려 효과를 확인한다.
6. **7b 실물 속도**: 실물 프로파일에서는 v ≤ 0.26, |ω| ≤ 1.82로 제한하되 곡률(ω/v)을 보존하도록 함께 줄인다. 가속 제한은 탐색 분기에도 적용한다. `speed_profile`(line_track 전용 주행 거리 창)은 실물·평가 맵 프로파일에서 끈다.

## 재현하지 못한 것과 한계

- 실물 하드웨어(OpenCR 펌웨어의 명령 제한·타임아웃)는 시험하지 않았다. 7b의 곡률 왜곡은 "선속도와 각속도를 각각 잘라낸다"는 가정 아래 명령 로그로 계산한 값이다.
- 평가 맵의 실제 크기와 길이는 모른다. 5a(14 m 미만)와 9(축별 4.7 m 초과)는 직접 만든 맵(`maps/short_t`, `maps/far`)으로 재현했다.
- 실행 PC에서는 `launch_nodelay`의 영상이 odom보다 40–60 ms 늦을 뿐이었다. 영상이 크게 늦는 상황은 image_bridge를 10 s 늦게 띄워 흉내 냈다(`camera_late`).
- IMU 정지를 처음에는 Python 릴레이(`imu_freeze_relay`)로 시험했다. 그런데 릴레이만 거쳐도 정지 없이 5구간 중 2번 ω≈3 rad/s 무한 회전이 생겨, IMU만 따로 띄운 `parameter_bridge`를 SIGSTOP하는 방식으로 다시 측정했다. odom 릴레이는 고장 전 구간 3/3이 정상이라 그대로 썼다.
- G2 bench(`bench.py --backend obstacle`, `runs/obstacles/*/obstacles.json`)는 8 cm 이탈 0.6 s 기준으로 회차를 끝낸다. 12회 중 11회가 상자에 닿기 전 첫 U턴에서 끝나 상자 판정을 못 했다. 그래서 이탈해도 끝내지 않는 `obs_*` 시나리오를 만들어 상자별 접촉을 셌다. 첫 U턴 실패(easy_22는 상자 없이도 4/4)는 안전 문제가 아니라 추종 성능 문제이므로 이 표의 판정에는 넣지 않았다.
- 대조군과 정상 시행에서도 추종이 가끔 실패했다(`imu_bridge_ctrl` r1 9.38 m, `camera_late` r2, `nobox_normal_28` r2). 고장 효과는 매번 고장 직후 1 s 안에 나타났으므로 판정에는 영향이 없다.
- `line_follower_bringup`은 C++ 패키지들에 의존해 따로 빌드하지 않았다. 하네스는 bench.py와 같이 소스 경로의 모델·브리지 설정을 쓰고, 8번 항목용으로 `line_follower`만 `install_s`에 빌드했다(시험 후 삭제).
