# line_follower 안전 가드(safety_guard) 적용 전/후 실측 요약

- 대상: `src/line_follower` rule 모드(`config/rule.yaml`)에 별도 노드 `safety_guard`를 추가했다. 팔로워는 명령 후보만 내부 토픽 `/line_follower/cmd_raw`로 내고, 가드가 `/cmd_vel`의 유일한 발행자다. 이전(가드 없음) 측정은 `../summary.md`(raw 스택)를 그대로 쓴다.
- 환경: `rp/ros2:jazzy-lab` 컨테이너 `lf_g`, headless Gazebo Harmonic. 고장 실험은 ROS 도메인 84–89, bench는 70–72, `GZ_PARTITION`은 `lf_g_*`, 동시에 돌린 시뮬레이션은 최대 2개다. 코디네이터 프로세스는 도메인 23에서 돌렸다.
- 측정 방식은 `../summary.md`와 같다. Gazebo 실제 자세(평가 전용)로 이동을 재고, `/cmd_vel`과 가드 상태 토픽 `/line_follower/safety`를 기록했다. "정지까지"는 고장 시점부터 로봇이 1 s 이상 정지(속도 < 1 cm/s, |ω| < 0.05 rad/s)하기 시작한 시각까지다. "정지 거리"는 그 사이 실제 경로 길이, "첫 0 명령"은 고장 뒤 처음 나온 0 `/cmd_vel`까지의 벽시계 시간이다.
- 결과 위치: 고장 회차는 `runs/<시나리오>/<시각>_r<k>/`(result.json, trace.npz, 로그)이고, 모음은 `all_results.json`이다. 랩은 `official_laps/`, 랜덤 6맵은 `random6_seed1457145442/`에 있다.


## 구성

```
follower_node --(/line_follower/cmd_raw, 명령 후보)--> safety_guard --(/cmd_vel, 유일한 발행자)--> 로봇
                                                        ^ /odom, /imu, /camera/image_raw (감시만 한다)
                                                        v /line_follower/safety (std_msgs/String JSON: state, reason, v, w, spin, 입력 나이)
```

- `follower_node.py` 코드는 계속 `/cmd_vel`에 발행한다. launch와 `run_guarded.py`가 이것을 `/line_follower/cmd_raw`로 remap한다. 그래서 팔로워만 돌리는 기존 기준선(`run_user.py`, bench, random_drive)은 바뀌지 않는다. 팔로워에서 고친 것은 종료 처리(`main()`)뿐이다.
- `launch/line_follower.launch.py`: 가드는 launch와 동시에 시작해 처음부터 0을 낸다. 팔로워는 지금처럼 `TimerAction(start_delay)` 뒤에 remap된 채 시작한다. 인자 `gui`, `mode`, `params`, `start_delay`는 그대로 두고 `safety:=sim|real`(기본 sim)과 `safety_params:=<yaml>`를 추가했다. `start_delay`는 가드의 출발 게이트에도 들어간다.
- `experiments/user_base/run_guarded.py`: 팔로워(`run_user.py` + remap)와 가드를 자식 프로세스로 띄운다. SIGINT와 SIGTERM은 둘 다에 전달한다. 팔로워가 죽어도 가드는 남아서 0을 유지한다. 가드가 죽으면 팔로워도 멈추고 종료 코드 1로 끝난다. 래퍼가 죽으면 자식은 `PR_SET_PDEATHSIG`로 SIGTERM을 받는다. 환경변수: `LF_PARAMS`, `LF_SAFETY_PARAMS`, `LF_START_DELAY`(기본 0), `LF_GUARD_ARGS`, `LF_GUARDED_PIDS`.
- `safety_faults.py`에 `--stack guarded|raw`를 추가했다. 가드 스택에서 `sigint`, `sigterm`, `sigkill`은 팔로워 프로세스만 죽인다. 새 시나리오는 `guard_sigint`, `guard_sigkill`(가드만 죽임), `stack_sigint`(래퍼에 SIGINT, Ctrl-C와 같은 경로), `gate_hold`(가드 게이트 20 s, 팔로워는 처음부터 동작)다. `compare`는 raw/가드 표를 만든다.

## 설계 결정과 이유

| 항목 | 결정 | 이유 |
|---|---|---|
| 출발 게이트 시계 | 가드가 시작된 뒤 **벽시계**(monotonic)로 `start_delay` 초가 지나고, `/odom`·`/imu`·`/camera/image_raw`를 모두 받은 뒤에 연다 | 20 s 규칙은 스톱워치로 재는 규칙이다. sim time은 실시간보다 빨리 갈 수 있어(RTF > 1) 게이트가 일찍 열릴 수 있지만 벽시계는 그럴 수 없다. 가드는 launch 직후에 뜨므로 게이트는 launch 기준 20 s보다 늦게 열린다. 단위 테스트에서 RTF 2로 확인했다 |
| 입력 나이 시계 | **ROS 시간**(Gazebo에서는 sim time). 그와 별도로 ROS 시계가 벽시계로 `clock_timeout` 동안 멈추면 정지한다 | 실측에서 IMU 수신 간격이 벽시계로 0.58 s 벌어졌을 때 sim time은 12 ms만 흘렀다(시뮬레이터가 잠깐 멈춤). 벽시계 나이로 쟀다면 0.5 s 타임아웃이 오정지를 냈을 것이다. 시뮬레이터가 멈추면 로봇도 움직이지 않는다. `/clock`이 아예 끊기는 경우는 clock 검사가 잡는다. 실물에서는 ROS 시간이 곧 시스템 시간이다. 가드 타이머는 steady clock이라 `/clock`이 끊겨도 계속 돈다 |
| 감시 방식 | 메시지 나이, 헤더 스탬프 정지(같은 샘플을 다시 내는 경우), IMU 내용 정지, odom 자세 정지. IMU 내용은 항상 본다. 실물이든 시뮬이든 IMU에는 노이즈가 있어서 비트까지 같은 샘플이 이어지면 고장이다. odom 자세는 가드가 움직이라고 명령하는 동안만 본다. 서 있을 때 자세가 같은 것은 정상이다. 카메라는 나이와 스탬프만 본다 | 이번 고장(브리지 정지)은 나이로 잡힌다. 실물 드라이버는 통신이 끊겨도 마지막 값을 새 스탬프로 계속 낼 수 있어 내용 검사를 넣었다. odom 내용 정지는 한 번 잡히면 자세가 다시 바뀔 때까지 정지를 유지해 멈춤과 출발이 반복되지 않게 했다. 영상 내용 비교는 CPU가 많이 들고, 정지 장면에서는 같은 영상이 정상이다 |
| 재개 / 래치 | 감시 정지는 모든 입력이 `recover_time`(시뮬 0.3 s, 실물 0.5 s) 동안 건강하면 **재개**한다. 실물 설정은 정지가 `latch_after` 3 s를 넘으면 래치한다. 비유한 명령과 회전 예산 초과는 **항상 래치**한다(재시작 필요) | 대회에서는 짧은 끊김 때문에 주행이 끝나면 안 된다. 실물에서 센서가 3 s 넘게 사라졌다면 고장이므로 사람이 확인해야 한다. NaN이나 inf는 소프트웨어 버그다. 회전 예산을 넘긴 뒤에는 로봇이 서 있어 팔로워가 새 정보를 얻지 못하므로 재개해도 소용이 없다 |
| 정지 방식 | 감시 정지는 **즉시 0**을 낸다(감속 제한 무시). 재출발은 0에서 가속 제한으로 서서히 올린다 | 위치를 모르는 상태에서 감속 램프를 쓰는 것은 위험하다. 재출발 램프 덕분에 막혀 있는 동안 팔로워가 속도를 올려 두었어도 점프가 없다 |
| 속도 제한 | v와 ω를 **같은 비율로** 줄여 곡률 ω/v를 유지한다. 가속 제한은 (v, ω)를 목표까지 직선으로 옮기는 방식이라, 0에서 출발하거나 0으로 설 때도 곡률이 그대로다 | v와 ω를 따로 자르면 명령의 5–6 %에서 곡률이 25 % 넘게 바뀌었다(기존 7b) |
| 시뮬 기본값 `safety_sim.yaml` | v 1.0 m/s, ω 4.0 rad/s. 가속 1.0 m/s²는 Gazebo DiffDrive의 `max_linear_acceleration`과 같다. 감속과 각가속 제한은 끈다. 회전 예산 30 s, 카메라 1.0 s, odom/IMU 0.5 s, 명령 0.3 s, clock 2.0 s, 래치 없음 | 팔로워 최대치(0.7 m/s, 3.0 rad/s)보다 크다. 팔로워는 급코너에서 v를 한 틱 만에 v_min으로 떨어뜨리고 ω를 한 틱에 3 rad/s까지 바꾼다. 감속이나 각가속을 제한하면 주행이 바뀐다. **카메라 1.0 s**: 시뮬 카메라 자체가 헤더 스탬프 기준으로 최대 0.46 s씩 건너뛰었다(시뮬 2개 동시, 약 13 Hz). 처음 0.5 s로 돌린 랩 3회 중 1회에서 결승 2 s 전에 0.38 s 오정지가 났다 |
| 실물 설정 `safety_real.yaml` | v 0.26 m/s, ω 1.82 rad/s(곡률 유지). 가속 0.5, 감속 1.0 m/s², 각가속 4.0 rad/s². 모든 센서 0.5 s, 회전 예산 8 s, 3 s 넘는 정지는 래치 | ROBOTIS Waffle Pi 한계값이다. 회전 예산 8 s와 가속 0.5 m/s²는 구 C++ 계층 값이다 |
| 회전 예산 | 제자리 회전은 \|ω\| > 0.05 rad/s이면서 \|v\| ≤ 0.02 m/s이거나 회전 반경 \|v/ω\| ≤ 5 cm인 경우다. 이 시간을 **누적**하고, 제자리 회전이 아닌 실제 이동이 `spin_reset_distance` 0.3 m를 넘을 때만 0으로 되돌린다 | 처음에는 "연속" 회전만 셌다. 그런데 Gazebo에서(`guard_sigkill` 첫 r2) 팔로워가 ω ±3 rad/s, v 0.06 m/s로 최대 2.8 s씩 돌다가 반경 0.1 m 호를 0.1–0.5 s 끼워 넣으며 220 s 동안 지름 0.5 m 안을 맴돌았고, 예산이 한 번도 차지 않았다. 구 C++ 계층의 "측정된 진행만 예산을 되돌린다"와 같은 규칙으로 바꿨고, 이 패턴은 단위 테스트로 넣었다. 공식 랩의 급코너 순간은 0.1 s 이하이고 사이에 긴 직진이 있어 영향이 없다 |
| 종료 시 0 | `rclpy.init(signal_handler_options=NO)`와 자체 SIGINT/SIGTERM 핸들러(플래그만 세운다)를 쓴다. 실행기를 멈춘 뒤 컨텍스트가 살아 있을 때 0을 20 ms 간격으로 5회 내고 DDS ACK를 기다린 다음 `shutdown`한다. 팔로워 `main()`도 같다 | rclpy 기본 핸들러가 컨텍스트를 먼저 끝내 0 발행이 RCLError로 실패하던 원인을 그대로 고쳤다. `run_user.py`는 `rclpy.init`을 감싸면서 인자를 버리므로, init 뒤에 rclpy 핸들러를 명시적으로 제거한다 |

- 고장마다 2회 이상 실행했다. 가드 스택에서는 팔로워 고장, 카메라, odom, IMU 고장 모두 **0.12–1.17 s 안에 정지했고 정지 거리는 0.01–0.41 m**다. raw 스택은 같은 고장에서 한 번도 서지 않았다(매트 이탈 또는 무한 회전).
- 1a/1b에서는 고친 팔로워 `main()`이 종료 직전에 0 후보를 내서 가드가 1–13 ms 안에 0을 전달했다. 0.3 s 뒤에는 command timeout으로 정지가 유지된다. 1c(SIGKILL)에서는 팔로워가 아무것도 못 내므로 `cmd_timeout` 0.3 s 뒤에 가드가 0을 낸다.
- `sigterm` r2의 "정지까지 0.64 s"는 이미 2 cm 안에 섰지만 차체 흔들림 때문에 정지 판정(1 s 연속)이 늦게 시작된 것이다. 정지 거리는 0.02 m다.
- 팔로워 SIGKILL 뒤 첫 회차에서는 가드 쪽 영상 수신이 약 0.5 s 끊겼다. 죽은 프로세스의 DDS 연결이 정리될 때 생기는 것으로 보인다. 이미 정지한 뒤라 영향은 없다.
- 유효하지 않은 회차: `stack_sigint`와 `guard_sigkill`의 첫 r2는 고장 지점(7.85 m)에 가지 못했다. `stack_sigint`는 하네스의 진행 추적이 3.4 m에서 끊겼다(로봇은 실제로 완주했고 팔로워 로그에 reached finish가 있다). `guard_sigkill`은 팔로워가 3.5 m에서 맴돌았다(위 회전 예산 항목). `launch_default` 첫 r2는 하네스가 상태 이벤트에 NaN 시각을 써서 result.json을 못 남겼다(고침). 세 경우 모두 같은 시나리오를 한 번씩 더 돌려 2회를 채웠다. `compare`는 고장이 일어나지 않은 회차를 빼고 계산한다.

## 남은 문제와 한계

1. **가드 자체의 크래시(SIGKILL)**: 가드가 죽으면 `/cmd_vel` 발행자가 없어지고, gz DiffDrive에는 명령 타임아웃이 없어 마지막 명령이 계속 유지된다(2/2 매트 이탈, 5 s 2.1–2.6 m). 노드 안에서는 고칠 수 없다. 실물에서는 펌웨어나 드라이버의 명령 타임아웃과 물리 E-STOP이 필요하다(design §9.2). `run_guarded.py`는 이때 팔로워를 멈추고 코드 1로 끝내 실패를 드러낸다.
2. **CPU**: 가드는 Python 노드로 코어 약 1/3을 쓴다(팔로워는 약 0.4). `/clock` 250 Hz와 IMU 200 Hz 콜백에 드는 rclpy 실행기 비용이 대부분이다(역직렬화는 약 1.6 %). Jazzy rclpy의 실험적 `EventsExecutor`로 줄일 수 있겠지만, 가드가 죽으면 마지막 명령이 남으므로 검증된 SingleThreadedExecutor를 유지했다. 이번 측정에서 랩 시간은 늘지 않았다.
3. **팔로워 시작 직후 0.3 s 멈춤**: 고장 회차 2/26에서 팔로워의 첫 영상 처리(약 0.3 s)가 명령 발행을 막아, 출발 직후(v < 0.05 m/s) command timeout 정지와 0.3 s 뒤 재개가 있었다. bench 랩에서는 일어나지 않았다. `cmd_timeout`을 늘리면 크래시 때 정지가 늦어지므로 0.3 s를 유지했다.
4. **시뮬 카메라 타임아웃 1.0 s**: 시뮬 카메라가 스스로 0.46 s까지 건너뛰므로 시뮬 기본값은 1.0 s다(카메라 상실 시 0.39 m 이동 후 정지). 실물 설정은 0.5 s다. 평가 PC가 더 느리면 다시 재야 한다.
5. 실물 설정은 Gazebo에서만 확인했다(공식 트랙 2/2 완주, 70.3–70.5 s). 실물 하드웨어 시험은 하지 않았다.
6. 팔로워 단독(`run_user.py`)에는 감시가 없다. 대회용 launch와 `run_guarded.py`에서만 가드가 붙는다. 다만 팔로워의 종료 시 0은 단독에서도 동작한다(프로세스 시험).
7. 이 측정은 `../summary.md`의 B 항목 중 1a, 1b, 1c, 2, 3a, 3b, 7b와 8(센서 준비)만 다룬다. 5a/5b(완주 판정)와 6(장애물)은 가드의 범위 밖이라 그대로 남아 있다.
